# Contributing

Contributions are welcome through issues and pull requests. Start a discussion in
an issue before adding a VM profile, changing address interpretation, or introducing
a dependency. Small fixes and regression tests can go straight to a pull request.

## Safety first

Do not submit real heap captures, strings, customer identifiers, tokens, keys,
environment files, or private capture reports. Reproduce bugs with generated bytes
or the Docker fixture. Read [SECURITY.md](SECURITY.md) for private reports.

## Local development

The CLI is Rust. Java and Maven are needed only for the fixture and run in Docker.
Use Docker with Compose v2, Python 3.10+ (standard library only), and an existing
Rust toolchain. CI pins Rust 1.96.0; the declared minimum is 1.88.

```sh
git clone https://github.com/clintonkavai/zgcmaster.git
cd zgcmaster
git switch -c fix/short-description
cargo fmt --all -- --check
cargo clippy --locked --all-targets -- -D warnings
cargo test --locked
cargo test --release --locked -- --include-ignored
python3 scripts/check_public_tree.py
python3 -m unittest discover -s scripts -p 'test_*.py'
```

Scale tests create temporary files, including a sparse 4 GiB+ file; allow enough
local disk capacity. Their cleanup runs after successful tests. Output under
`captures/`, `artifacts/`, and `target/` is intentionally ignored.

Exercise actual Java 21 layouts and reference encodings in both fixture modes:

```sh
python3 scripts/ci_fixture.py --profile nongen
python3 scripts/ci_fixture.py --profile generational
```

Each run builds pinned containers, starts only this project's fixture, captures
its backing file, checks it against independent expected data, and stops the
fixture even on failure. This takes several minutes and downloads images/Maven
dependencies. Do not run both profiles concurrently in the same Compose project.
It does not change host Java or Maven configuration. The fixture must remain bound
to localhost; its endpoints expose deliberately inspectable laboratory state.

## What a pull request needs

- A concrete failure or user-visible change, with a minimal synthetic reproduction.
- Regression tests for success, malformed input, limits, and refusal paths affected
  by the change. Changes to profiles/reference decoding need fixture evidence too.
- An explanation of memory/disk bounds and any new dependency or output field.
- Updated help/docs and a changelog entry when behavior changes.
- A statement of which checks you ran and which you could not run.

Preserve explicit uncertainty: candidates are not proven live objects; structural
hash checks do not authenticate class names. Never apply oop color masks to klass
identities, silently turn virtual references into offsets, or hide truncated
coverage. Keep existing output files intact and require a completion footer for
streams. See [IMPLEMENTATION-NOTES.md](IMPLEMENTATION-NOTES.md).

Use focused commits and descriptive titles. CI runs on pull requests with
read-only permissions and no project secrets. Maintainers review changes before
merging; passing CI alone does not establish correctness on arbitrary heaps.
